# 轻量级 Git 管理工具 —— 技术选型与架构规划

> 目标：功能对齐 IntelliJ IDEA 的 Git 工具窗口，同时把内存占用压到 Electron 方案的 1/5 以下，并支持多窗口同时管理不同仓库。
> 编制日期：2026-10-14

---

## 0. 结论摘要（TL;DR）

| 决策项 | 结论 | 核心理由 |
|---|---|---|
| 开发语言 | **Rust** | 无 GC、无运行时、内存安全；零成本抽象让"低内存"与"高性能"不互斥 |
| GUI 框架 | **Slint（软件渲染 / femtovg 后端）**为第一方案；**egui（glow 后端）**为许可证友好备选 | 保留模式 + 无 GPU 依赖，社区实测可从 135MB 压到约 30MB；多窗口是一等公民 |
| Git 内核 | **三层混合：gix（读热路径）→ git2（写补充）→ git CLI 子进程（兜底）** | gix 到 2026 年仍未实现 push / rebase / merge commit / hooks / reset，单一内核无法做到功能对齐 |
| 进程模型 | **单进程多窗口**为默认；**多进程**作为可选隔离模式 | 单进程共享缓存与监听器，3 窗口总内存可控制在 90MB 以内 |
| 目标内存 | 空闲 **< 40MB**，3 窗口 **< 90MB** | 对比 Electron 单窗口空闲 168MB、6 窗口 409MB |
| 明确排除 | Electron、Flutter Desktop、CEF | 架构级内存下限锁死，无法通过编码优化突破 |

**一句话方案：Rust + Slint + gix/git2/CLI 三路 Git 内核 + 单进程多窗口 + 全程虚拟化渲染。**

## 1. 需求拆解与技术含义

| 原始需求 | 技术含义 | 影响的架构决策 |
|---|---|---|
| 对齐 IDEA Git 工具窗口功能 | 需要提交图（多分支泳道）、三路差异、逐行暂存、冲突合并编辑器、Blame、文件历史 | UI 框架必须支持自绘 + 列表虚拟化；必须有可靠的 rebase/merge 后端 |
| 极低内存占用 | 常驻 RSS 是硬指标，不是"够用就行" | 排除 WebView/JS 引擎/GC 虚拟机；packfile 走 mmap；所有视图虚拟化 |
| 可视化配置界面 | 主题、字体、外部 diff/merge 工具、凭据、缓存预算、快捷键 | 需要独立的设置子系统 + 配置文件持久化（TOML） |
| 多开窗口管理不同仓库 | N 个仓库窗口并存，互不干扰，内存不线性膨胀 | 缓存全局共享；窗口级独立视图状态；仓库级写锁防冲突 |

关键洞察：**"低内存"和"多窗口"是同一个问题**——如果每个窗口复制一份缓存和一份渲染引擎，多窗口必然内存爆炸。所以架构必须从一开始就按"共享内核 + 轻量视图"来设计。

## 2. 语言与 GUI 框架选型

### 2.1 候选矩阵

| 方案 | 单窗口 RSS | 6 窗口总 RSS | 冷启动 | 安装包 | 自绘/虚拟化能力 | 许可证 |
|---|---|---|---|---|---|---|
| Electron（Chromium + Node） | ~168MB | ~409MB | 2–5s | 80–150MB | 强（但代价高） | MIT |
| Tauri 2（Rust + 系统 WebView2） | ~42MB | ~172MB | 0.3–1s | 3–12MB | 受 DOM/JS 制约 | MIT/Apache |
| Flutter Desktop（Skia + Dart VM） | ~90–140MB | 线性增长明显 | 0.8–2s | 40–80MB | 强 | BSD |
| C++ / Qt Widgets | ~60–90MB | ~200MB | 0.3–0.8s | 30–60MB | 强（QAbstractItemModel 成熟） | LGPL / 商业 |
| Rust + egui（glow/wgpu 自绘） | ~135MB（GPU 后端实测） | ~340MB（估算） | 0.1–0.4s | 5–20MB | 强，即时模式 | MIT/Apache |
| **Rust + Slint（软件渲染）** | **~28–35MB** | **~70–90MB（估算）** | 0.1–0.3s | 5–15MB | 强，保留模式 + 自绘 | GPLv3 / 商业 |

> 数据说明：Electron、Tauri 的数据来自公开的多窗口基准测试（6 窗口场景）；egui 135MB 与 Slint 30MB 来自同一应用的迁移实测；Qt、Flutter 与 6 窗口推算值为量级估算，需在 POC 阶段实测校准。所有数值随仓库规模、渲染后端、操作系统差异较大，**只用于量级比较，不应作为精确承诺**。

### 2.2 为什么排除 WebView 系与 Flutter

1. **Electron 是架构级不可能**。每个窗口一个 Chromium renderer 进程，空闲内存下限被锁死，任何代码优化都无法突破。与"极低内存"需求直接冲突。
2. **Tauri 2 是"次优但可接受"**，不是最优。它靠系统 WebView2 共享进程池把多窗口内存压到 172MB，比 Electron 好 58%，但：
   - 内存下限由 WebView2 决定，你无法控制（Windows 上是 evergreen 运行时，版本随系统漂移）；
   - 高吞吐数据（比如 10 万条 commit 的列表、大文件 diff）经过 `invoke` 的 serde_json 序列化会成为瓶颈，需要自建二进制通道；
   - Linux 上 WebKitGTK 的 ABI 分裂（4.0 vs 4.1）会带来打包摩擦。
   - 对一个"以低内存为核心卖点"的工具，多付 100MB+ 只为了用 Web 技术写 UI，性价比不成立。
3. **Flutter Desktop 内存并不低**。它捆绑 Skia 渲染栈与 Dart VM，且没有成熟的"软件渲染低内存模式"。

### 2.3 为什么首选 Slint 而不是 egui / iced / Qt

**Slint 的决定性优势是"可以不依赖 GPU"。** 一个 Git 客户端是**低交互频率**的工具类应用——大部分时间是静止的，等待用户滚动或点击。这正好是软件渲染的最佳场景：

- 省掉 GPU 上下文的常驻分配（D3D/OpenGL 驱动侧通常有几十 MB 级别的不可控占用），这是那个 135MB → 30MB 案例的根因；
- 保留模式（retained mode）意味着布局在状态不变时不需要每帧重算，多窗口与动态面板切换时无布局抖动，CPU 空闲接近休眠；
- 声明式 DSL 把 UI 与业务逻辑分离，编译期生成高效渲染代码，无 JS 引擎、无 DOM、无 VM；
- 多窗口是一等公民，一个事件循环管理 N 个 `Window`，天然契合"多窗口管理多仓库"。

**egui 作为备选的理由**：全部逻辑用纯 Rust 写，不需要额外学 DSL，原型速度最快，且是 MIT/Apache 双许可。代价是——它是即时模式（immediate mode），复杂自适应界面需要额外代码控制重绘；并且它**没有一等公民的软件渲染后端**，最低内存路径仍要经过 GPU 栈（约 135MB 级别）。

**iced / Qt 的取舍**：iced 架构清晰但多窗口支持与生态弱于前两者；Qt Widgets 在"做这类应用"上开发效率最高（`QAbstractItemModel` 天生支持百万行虚拟化、`QPlainTextEdit` 自带语法高亮框架），若团队 Qt 熟练、对 60–90MB 的内存可接受、且看重交付速度，它是完全合理的第二路线——但它达不到"极低内存"。

### 2.4 必须提前确认的许可风险（重要）

**Slint 采用 GPLv3 + 商业双许可**，不是 MIT/Apache。这意味着：

- 如果你计划**闭源商用**发布，必须取得 Slint 的商业授权（官方提供面向中小团队的免版税条款，但具体适用条件与营收门槛需以其最新许可协议为准，请在 POC 前先确认清楚）；
- 如果产品计划**开源且可接受 GPLv3**，则无额外成本。

**如果闭源且不愿付授权费，请直接切换为 egui（MIT/Apache）**，并把内存目标调整为"单窗口 < 80MB、3 窗口 < 180MB"——这仍然是对 Electron 的碾压级优势。

这个决策应在写第一行代码之前完成，因为它决定整个 UI 层的技术栈，后期切换成本极高。

### 2.5 选型风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| Slint 生态体量小于 egui/Tauri | 遇到问题时可参考资料少 | 在 M0 阶段用真实需求压测，验证自绘分支图与虚拟列表能力 |
| Slint DSL 学习曲线 | 团队上手慢 | 限制 DSL 只用于布局与样式，所有业务逻辑留在 Rust 侧 |
| 软件渲染在超宽屏/高 DPI 下的 CPU 占用 | 滚动时掉帧 | 全视图虚拟化（只渲染可见行）+ 增量重绘 + 实测校准 |
| Slint 许可模式变化 | 法律成本 | 锁版本 + 法务前置评审 |

## 3. Git 内核选型（本项目最关键的技术决策）

### 3.1 2026 年的现状

- **gix（gitoxide）**：纯 Rust 实现，内存安全，无 FFI 边界，被 Jujutsu、GitButler 采用，Cargo 也已用它做依赖拉取。读侧（clone、fetch、status、diff、blame、revwalk、object/ref 读写）. **但截至 2026-10，以下功能仍未实现或未达生产可用：`push`、`rebase`、`merge commit`、`hooks`、`reset`。** CLI 工具（gix/ein）官方明确标注不稳定，不可用于脚本。
- **git2（libgit2 绑定）**：功能覆盖广，但 API 成熟度高的是"机制"层（对象、索引、树、引用），高级 porcelain（交互式 rebase、submodule 递归、LFS）仍要自己做或走 CLI。有 FFI 边界与 C 代码的内存安全风险。
- **git CLI 子进程**：永远正确、永远完整（它就是真相标准），代价是进程启动开销与输出解析。

**结论：没有任何单一内核能同时满足"功能对齐 IDEA"和"低内存"。必须分层。**

### 3.2 三路路由表

| 能力 | 主实现 | 兜底 | 理由 |
|---|---|---|---|
| 提交图遍历 / revwalk | **gix** | — | 流式、可并行、mmap，性能与内存最优 |
| 状态（working tree / index） | **gix-status** | git2 | 增量计算，避免全量扫描 |
| Diff（行/词级） | **gix-diff + imara-diff（Histogram 算法）** | git CLI | Histogram 比 Myers 快 10%–100%，比 `similar` crate 快至多 30×；gix 内部即用 gix-imara-diff |
| Blame / annotate | **gix-blame** | git CLI | 读型操作，适合内存驻留 |
| 引用 / 分支 / 标签管理 | **gix-ref** | git CLI | 纯读写 refs，低风险 |
| 暂存 / 反暂存（含逐行 hunk） | **gix-index** | git2 | 索引写入，需事务性保证 |
| 提交 / 修订（--amend） | **gix**（object write + commit） | git CLI | |
| 检出 / 分支切换 | **gix checkout** | git CLI | 复杂情况（未跟踪文件冲突）交给 CLI |
| **Merge（含策略与冲突标记）** | **git2** | **git CLI** | gix 未实现 merge commit |
| **Rebase（普通 / 交互式）** | **git CLI** | — | gix 完全未实现；交互式 rebase 本质是序列编辑器，自己实现性价比极低 |
| **Cherry-pick / Revert** | **git2** | git CLI | |
| **Reset（soft/mixed/hard）** | **git CLI** | — | gix 未实现 |
| **Push** | **git CLI** | gix（跟踪中） | gix 的 push 尚未落地 |
| Fetch / Pull | gix 或 git CLI | — | 两者皆可，建议统一走 CLI 以保证凭据与 hook 行为一致 |
| Stash | **git CLI** | git2 | 语义复杂（含 untracked、staged 组合） |
| Submodule | **git CLI** | — | 递归语义复杂 |
| **Hooks** | **git CLI** | — | gix 无 hooks 支持，而用户依赖它（commit-msg、pre-commit） |
| LFS / Sparse-checkout / Partial clone | **git CLI** | — | 生态只在 CLI 侧完整 |
| 凭据（SSH agent / HTTPS token / credential helper） | **git CLI 的 credential 协议** | 自建 | 直接复刻用户既有配置，零额外配置成本 |

**设计原则：读型高频操作必须留在进程内（gix），写型低频且语义复杂的操作走子进程。** 这样既拿到了低内存（高频路径不产生进程），又拿到了 100% 的功能覆盖与"永远和命令行行为一致"的正确性保证。

### 3.3 内存与线程的关键约束

- **gix 的 packfile 走 mmap**：对象数据由操作系统 page cache 承载，不计入进程私有堆。这是 Rust 方案内存低的核心机制之一。切勿把大对象 `read_to_end` 到 `Vec<u8>`。
- **git2 的 `Repository` 句柄不是线程安全的写对象**：每个工作线程应持有独立的 `Repository` 实例（内部会共享 odb 缓存），写入操作必须串行化到仓库级互斥锁。
- **git CLI 子进程必须设上限**：并发子进程数 ≤ 4，否则一次"拉取所有分支"可能瞬间起十几个 git 进程把内存吃光。
- **所有子进程输出必须流式解析**，禁止 `Command::output()` 一次性读入完整 stdout（大仓库的 `git log` 可以是几百 MB）。

## 4. 架构设计

### 4.1 分层结构

```
┌─────────────────────────────────────────────────────────┐
│  UI 层（单事件循环，承载 N 个窗口，每窗口绑定一个仓库）   │
│  Local Changes │ Log + 分支图 │ Diff │ 合并编辑器 │ 设置  │
├─────────────────────────────────────────────────────────┤
│  命令总线：请求代次号 + 取消令牌 + 结果增量合并            │
│  （UI 线程只投递消息与消费增量，永不执行 I/O）            │
├─────────────────────────────────────────────────────────┤
│  Git 服务层（有界工作线程池，线程数 = min(4, CPU 核数)）  │
│  ┌───────────┐ ┌──────────────┐ ┌──────────────┐        │
│  │ gix       │ │ git2 + CLI   │ │ notify       │        │
│  │ 读取热路径 │ │ 写入 / 兜底   │ │ 文件变更监听  │        │
│  └───────────┘ └──────────────┘ └──────────────┘        │
├─────────────────────────────────────────────────────────┤
│  数据层：packfile(mmap) · refs · index · commit-graph    │
│          LRU 缓存（硬上限，全局共享）                     │
└─────────────────────────────────────────────────────────┘
```

### 4.2 进程与线程模型

**默认：单进程多窗口。**

- 一个进程、一个 UI 事件循环、N 个原生窗口，每个窗口绑定一个仓库；
- 所有窗口**共享**同一份 LRU 缓存、同一份 packfile 映射、同一个工作线程池；
- 每窗口只持有自己的**视图状态**（滚动位置、当前选中行、面板展开状态），这部分是 KB 级；
- 结果：第 2、3 个窗口的边际内存开销约 10MB/窗口，而非复制整个内核。

**可选：多进程隔离模式（`--isolate`）。**

- 每个窗口独立进程，一个窗口崩溃不影响其他窗口；
- 代价是每进程重复一份基线开销（约 +28MB/窗口）；
- 适用于"长期挂着 8 个仓库盯着"的极端场景，按需开启。

**仓库写锁**：每个仓库路径加一个锁文件（`.git/<tool>.lock`，存 PID）。若已有实例占用，新实例以只读模式打开并提示，避免两个进程同时写 index 导致仓库损坏。这也意味着**同一仓库不允许重复多开**，多窗口只针对不同仓库——与需求一致。

**UI 线程纪律**：UI 线程上不允许出现任何文件 I/O、网络、进程启动。违反此约束是本类工具卡顿的第一大来源。

### 4.3 非阻塞请求生命周期

每一次 Git 操作（打开仓库、切分支、加载下一页日志、计算 diff）都走同一条路径：

1. UI 线程投递请求消息（入队即返回）；
2. 分配**单调递增的请求代次号**并附带**取消令牌**；
3. 投递到有界工作线程池；
4. 工作线程执行 gix 调用或启动 git 子进程；
5. 结果分片回传，UI 线程增量合并到视图模型；
6. **若该请求的代次号已过期（用户已切换仓库/改了筛选条件），结果直接丢弃**。

第 6 点是"性能稳定"的关键：它让"快速在多个仓库窗口间切换"不会产生结果错乱，也让长耗时操作（大仓库 revwalk）可以被即时放弃而不阻塞。

### 4.4 Cargo workspace 划分

```
git-tool/
├── crates/
│   ├── gt-core/        # 领域模型：Commit/Ref/Change/RepoId，无 I/O 依赖
│   ├── gt-backend/     # Git 内核抽象层：统一 trait，路由到 gix / git2 / CLI
│   ├── gt-service/     # 工作线程池、请求代次、取消令牌、LRU 缓存、notify 监听
│   ├── gt-diff/        # 差异计算与 hunk 模型（gix-diff + imara-diff）
│   ├── gt-graph/       # 提交图泳道布局算法（增量 + 可缓存）
│   ├── gt-config/      # TOML 配置、主题、快捷键、外部工具绑定
│   └── gt-ui/          # Slint 组件与各窗口视图
└── app/                # 二进制入口、窗口管理、单实例守卫
```

**为什么拆 crate**：`gt-backend` 的内核路由是这个项目最大的技术风险，独立成 crate 后可以在不启动 GUI 的情况下做完整的集成测试（用真实仓库跑"gix 结果 vs git CLI 结果"的对比测试）。

## 5. 低内存工程手段（逐条落实）

这些不是优化建议，而是架构约束——每一条不进 POC 验收就不算完成。

1. **列表全虚拟化**：10 万条 commit 的 Log 只渲染视口内的约 40 行。Slint 的 `ListView` 与 egui 的 `show_rows` 都支持。
2. **提交图增量计算**：泳道布局随分页加载增量推进，不预先为全量历史分配内存。
3. **packfile 走 mmap**，对象内容零拷贝借用（`&[u8]` / `Arc<[u8]>`），不复制到堆。
4. **硬上限 LRU 缓存**：全局统一预算（建议初始 32MB），分三段配额——提交图节点、diff hunk、blob 文本。超限按 LRU 淘汰，绝不"自动扩容"。
5. **大于阈值的文件不做 diff**：单文件 > 2MB 或检测为二进制时，直接显示占位（"二进制文件 / 文件过大"），与 IDEA 行为一致。这是防止内存尖峰最有效的一刀。
6. **diff 流式产出**：`imara-diff` 的 `Sink` 边算边产出变更块，不物化完整编辑脚本。
7. **语法高亮惰性化**：只对可见行做高亮，滚动时增量补齐，缓存按行号淘汰。
8. **字符串驻留**：commit 元数据（作者、邮箱、提交信息首行）用全局驻留表，SHA 用 u32 内部索引而非 `String`。
9. **窗口关闭即释放**：关闭仓库窗口时主动 drop 该仓库的视图模型与缓存分区，不等 GC（Rust 本就没有 GC，但要确保 `Arc` 引用计数真正归零，注意避免监听器线程持有强引用形成环）。
10. **构建配置**：`lto = "fat"`、`codegen-units = 1`、`panic = "unwind"`（**不要用 abort**，否则工作线程无法用 `catch_unwind` 做崩溃隔离）、`strip = true`。

## 7. 稳定性与正确性工程

这是容易被"能跑就行"的原型阶段忽略、但在正式产品中决定生死的部分。

1. **一致性测试（最重要）**：对同一批真实仓库（小/中/大/超大型各一），断言"我们的 status/diff/log 输出 == `git` CLI 的输出"。任何不一致都视为 P0 缺陷。这个测试套件应当在 CI 中对固定的仓库快照运行。
2. **工作线程崩溃隔离**：工作线程包 `catch_unwind`，单次 Git 操作 panic 只让该请求失败并提示用户，不拖垮 UI。
3. **子进程超时与可杀**：所有 git 子进程设超时（网络操作 120s，本地操作 30s），持 `Child` 句柄以便用户取消时能真正 kill 掉进程树。
4. **大仓库性能基准**：建立稳定的基准仓库（建议用 Linux 内核或 Rust 编译器仓库的历史快照），CI 中跑内存与耗时回归，**设定内存上限断言，超出即失败**。没有回归基准，"低内存"这个卖点会在三个月内自然腐化。
5. **文件监听去抖**：`notify` 事件在 200–300ms 窗口内合并，避免 `git checkout` 触发数千次事件把 UI 线程刷爆。同时必须过滤 `.git/objects` 等内部目录，否则每次 fetch 都会引发风暴。
6. **只读降级**：任何写操作失败时，工具必须能安全降级为只读模式而不是留下半完成状态（例如 rebase 中断后正确提示 `--continue` / `--abort` 路径）。
7. **跨平台**：Windows 上的长路径（>260 字符）、大小写不敏感文件系统、CRLF 自动转换；macOS 的 Unicode 归一化（NFD）；Linux 的权限位。这三类是 Git GUI 最常见的兼容性缺陷来源。

## 8. 里程碑规划

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **M0 技术验证（最关键）** | 验证三个假设成立 | ① Slint 单进程开 3 窗口，总 RSS < 90MB；② gix 打开 Linux 内核仓库并虚拟化滚动 100 万条 Log，UI 不掉帧、内存不持续增长；③ gix 的 status/diff 与 git CLI 输出一致 |
| **M1 只读 MVP** | 能看不能改 | 打开仓库、Log + 分支图、Diff 查看、状态列表、多窗口 |
| **M2 本地写入** | 能改本地 | 暂存（含 hunk 级）、提交、amend、分支增删改、检出、丢弃更改 |
| **M3 远端** | 能同步 | Fetch / Pull / Push + 凭据管理（SSH agent 与 HTTPS token 全覆盖） |
| **M4 高级操作** | 对齐 IDEA 主体功能 | Merge、Rebase（含交互式）、Cherry-pick、Revert、Reset、Stash、冲突三路编辑器 |
| **M5 打磨** | 产品化 | 图形化设置界面、Blame 与文件历史、外部工具绑定、主题、内存回归基准进 CI |
| **M6 可选** | 平台集成 | 代码托管平台 PR/MR 面板、LFS 可视化、提交签名 UI |

**M0 的结论决定后续一切。** 如果 M0 中 Slint 的软件渲染在滚动大列表时 CPU 占用不可接受，或 Slint 许可无法接受，此时切换到 egui 的成本只有 2–3 周；到 M4 再切换则是重写。

## 9. 关键风险与待确认决策点

| # | 决策点 | 影响范围 | 建议 |
|---|---|---|---|
| 1 | **产品是否闭源商用？** | 决定 Slint vs egui，进而决定整体内存水平 | **写第一行代码前必须确认**；闭源不愿付费 → 选 egui |
| 2 | 是否接受"极少数操作走 git CLI"？ | 决定能否功能对齐，也决定了是否需要依赖用户机器上有 git | 建议接受。可在启动时探测 git 可执行文件，缺失则降级并明确提示 |
| 3 | 是否需要支持 Windows 之外的平台？ | 影响渲染后端与凭据实现的工作量 | 建议 M1 只做当前平台，M5 再横向补齐 |
| 4 | 提交图是否需要支持"显示全部远程分支"？ | 大仓库下 revwalk 规模可能爆炸 | 建议默认只显示本地 + 当前跟踪分支，全量作为显式选项 |
| 5 | 是否需要支持超大仓库（monorepo，>500 万 commit）？ | 决定是否需要 commit-graph 预计算与磁盘缓存 | 若需要，把 commit-graph 缓存作为 M2 的独立任务 |

## 附录 B：参考事实来源

- gitoxide（gix）功能完整度：截至 2026-10，push / rebase / merge commit / hooks / reset 仍未实现；被 Jujutsu、GitButler 采用；Cargo 已用于依赖拉取。
- Slint vs egui 内存：公开案例显示 Rust GUI 应用从 egui 迁移到 Slint 并经软件渲染后，内存由约 135MB 降至约 30MB。

- imara-diff：Histogram 算法较 Myers 快 10%–100%，较 `similar` crate 在复杂 diff 上快至多 30×。
