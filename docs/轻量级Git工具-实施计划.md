## 0. 计划编制说明

- **估算单位**：人周（pw），以"1 名熟练 Rust 工程师"为基准；两人并行时标注可压缩项。
- **总体规模**：约 29–34 pw（单人串行），关键路径 22–26 周（两人并行）。
- **计划原则**：
  1. **M0 是一切的前提**——4 项 POC 不全过，不进入功能开发（架构规划 8 节原则的细化）；
  2. **测试基础设施先行**——一致性测试（NFR-COR-01）从 M0 就开始建设，而非 M5 补课；
  3. **纵切优先**——每个里程碑交付"能跑的端到端切片"，而非横向堆功能；
  4. **每阶段末尾设决策门**（Go/No-Go），见第 8 节。

## 3. M0：技术验证（3 pw，POC 详细计划）

> M0 的结论决定后续一切。以下 4 项 POC 各自独立成 demo（不在主 workspace 强行集成），每项必须产出**可复现的数据**（内存采样、帧时间分布、一致性 diff 报告）。

### POC-1 Slint 软件渲染多窗口内存（0.5 pw）

- 内容：Slint（femtovg 软件渲染）单进程开 3 个独立窗口，每窗口模拟真实视图（虚拟列表 1 万行 + 分支图绘制），挂起 60s 采样 RSS。
- **通过判据**：3 窗口总 RSS < 90MB，单窗口空闲 < 40MB（NFR-MEM-01/02）。
- 失败预案：记录实测下限 → 触发 egui 重评（此时切换成本 2–3 周，架构规划 8 节）。
- 附加：验证多显示器 / 高 DPI / 超宽屏下滚动 CPU 占用（架构规划 2.5 风险项）。

### POC-2 gix 大仓库虚拟化滚动（1 pw）

- 内容：gix revwalk 打开 Linux 内核仓库，UI 虚拟列表滚动 100 万提交，采样帧时间与 RSS 曲线。
- **通过判据**：P95 帧时间 < 33ms；滚动 10 分钟 RSS 增幅 < 10%（NFR-PRF-02、NFR-MEM-03）。
- 技术要点：分页加载（每批 500–2000）、packfile mmap 零拷贝验证、字符串驻留验证（架构规划 5.2/5.8）。

### POC-3 gix 与 CLI 一致性（1 pw）

- 内容：对 4 个基准仓库，`gix status/diff/log` 与 `git` CLI 输出做结构化对比（porcelain v1、numstat、rev-list）。
- **通过判据**：4 仓库全量输出一致（NFR-COR-01）。
- 产出：**这个对比脚本直接固化为 CI 一致性测试套件的 v0**——POC 代码不丢弃，成为 `gt-backend` 的测试资产。

### POC-4 泳道图增量布局算法（0.5 pw）

- 内容：脱离 UI 单测 gt-graph 算法：100 万提交的泳道布局、IntelliSort 拓扑排序切换、折叠/展开单条线性分支。
- **通过判据**：切换排序 / 折叠分支 → 增量更新 < 50ms 且只重排受影响泳道（FR-LOG-05 验收）。
- 失败预案：若增量布局复杂度超标，降级方案为"折叠操作触发视口内重排 + 视口外延迟重排"，写入 G0 评审结论。

### G0 决策门（M0 末尾，0.5 pw 含评审）

- 输入：4 项 POC 数据报告。
- **全部通过** → 锁定技术栈，进入 M1。
- **POC-1 失败** → 启动 egui 应急路线（内存目标改单窗口 < 80MB / 3 窗口 < 180MB，需用户重新确认卖点口径）。
- **POC-2/3/4 部分失败** → 逐项评审降级方案（分页策略 / 路由表调整 / 布局降级），失败项不得静默带入 M1。
