## 4. 关键设计与取舍（写给后来者）

### 4.1 远端操作全部走 git CLI，不做 gix 原生实现

路由表允许 fetch/pull 走 gix，本阶段统一选了 CLI，理由不是"省事"：

- **凭据协议是拉取式的**。credential helper、SSH agent、企业 CA、代理只对 git 本体生效；
  自己实现等于要求用户再配一遍，而且永远追不上二次验证与 SSO 的边界情况。
- **推送结果的语义只在 CLI 侧完整**。`push --porcelain` 精确到每个 ref 的标志位与
  拒绝原因（`[rejected] (non-fast-forward)` / `[remote rejected] (pre-receive hook declined)`），
  这正是"被拒引导"的数据源。
- 代价：每次操作一个子进程。网络操作本来就是秒级等待，且受并发上限约束；读热路径仍走 gix。

### 4.2 取消为什么必须杀进程树，且收尾要有上限

`Child::kill()` 只杀直接子进程。git 的网络操作几乎总会派生后代
（`git-remote-https`、`ssh`、`git-upload-pack`），孤儿会继续占着连接与管道。
更隐蔽的是：**管道写端被后代继承**，读取线程要等最后一个持有者退出才收到 EOF，
于是"取消"会变成"等到命令自己跑完"。

因此这里是两层防线：

1. `taskkill /PID <pid> /T /F` 杀进程树；
2. 收尾 join 改为**有界等待**（1.5s）：超时就放弃读取线程并记一条 warn。
   实测中第二层救了一次 —— 并行跑测试时 taskkill 偶发未覆盖到孙进程，
   没有上限的话取消要等满 20s（该现象已固化为回归用例）。

### 4.3 强制推送的两个闸门

`--force-with-lease` 而不是 `--force`：前者在"远端在你上次 fetch 之后被推进"时失败，
不会静默覆盖别人的提交。此外受保护分支**双重拦截**（界面 + 服务层），
因为服务层可能被其他调用方复用，界面的判断不能当作安全边界。

### 4.4 网络独占槽位的顺序问题（已修）

最初的实现是"先推进网络通道代次，再抢占独占槽位"。这会导致：
用户在 fetch 进行中点 Push → 代次推进**取消了正在跑的 fetch** → 随后抢槽失败 →
"推送被拒，同时 fetch 莫名停了"。
修法是**先抢槽、后推进代次**，并在测试里钉住"被拒绝的抢占不能影响已占用的槽位"
（`network_slot_is_exclusive_and_released`）。

### 4.5 凭据注入用 `GIT_ASKPASS`，不用命令行参数

口令进命令行会被任务管理器/`ps` 看到，也会进审计记录。`GIT_ASKPASS` 让 git
在需要时反向调用本程序，口令只存在于**该子进程的环境变量**里，随进程消失。
`--askpass` 分支必须在任何初始化之前处理：stdout 上多一行日志就等于错误的口令。

### 4.6 脱敏发生在写环形缓冲之前

Console 会被导出、贴进 issue。如果"展示时再脱敏"，脱敏漏一处就会把 token
写进用户的 bug 报告。因此 `redact` 在 `GitCli::record` 里执行，
args / command_line / stdout / stderr / error 五个字段全覆盖。

`git -c alias.knotwork-stall='!sleep 20' knotwork-stall` 在 300ms 后被取消：
返回 `BackendError::Cancelled`，总耗时 < 1s（含 1.5s 上限内的管道收尾）。

### 6.4 操作等价（L3，节选）

`fetch_and_pull_match_the_cli_after_the_remote_moves` —— 远端被第三个克隆推进后，
A 走 `RemoteOps`、B 走 `git fetch`：`refs/remotes/origin/main` **逐字符相同**；
再各做一次合并式 pull，`HEAD^{tree}` 与 `git status --porcelain` 完全一致。

`push_produces_the_same_remote_state_as_the_cli` —— 两侧提交 id 相同（固定作者与提交时间），
推送后裸仓库 `refs/heads/main`、本地 `refs/remotes/origin/main`、上游配置三者全部相同。

## 7. G3 结论

**有条件通过。**

- 远端链路的**正确性**用最强的方式钉住了：L3 套件以"git 自己的输出"为基准，
  6 个用例覆盖 push / fetch / pull / 拒绝 / 远端配置 / 预览计数，
  且在**提交 id 相同**的前提下比对引用值，不存在"看起来差不多"；
- 并发上限、超时、取消（含进程树）四项约束**在真实长跑命令上验证**，
  并因此发现并修复了两个真实缺陷（取消被管道阻塞、独占槽位顺序颠倒）；
- 凭据安全可按代码与测试审计：明文不落盘、审计前脱敏、诊断文案不泄露 token；
- **唯一未完成的是真实 SSH/HTTPS 双路径的端到端验收** —— 这需要一台带凭据的机器，
  不是代码问题，但按需求文档的字面口径，G3 不能在缺少这一步的情况下判"通过"。

进入 M4 前建议：

1. 先按 §5.1-A 的清单在有凭据的环境补一次双路径走查，把结果附到本报告后即可关闭 G3；
2. M4 的 merge/rebase 会第一次引入**需要长时间持有仓库锁**的操作，
   届时复核"网络通道与写通道"的互斥关系：当前两者互不阻塞（网络独占只作用于网络），
   在 rebase 进行中发起 fetch 是允许的，需要确认 git 自身对这些组合的容忍度。
