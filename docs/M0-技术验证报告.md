# M0 技术验证报告（G0 决策门）

> 对应《轻量级Git工具-实施计划.md》第 3 节 M0 与第 3 节末 G0 决策门。
> 4 项 POC 的代码位于 `pocs/`，运行方式见 `pocs/README.md`。
> 数据采集日期：2026-10-15；构建档位：Windows / `x86_64-pc-windows-msvc`；
> 渲染后端：`winit-software`（软件渲染）。

---

## 1. 结论摘要

**4 项 POC 全部通过 G0 决策门**，技术栈锁定不变（Rust + Slint 软件渲染 +
gix/git2/CLI 三路内核 + 单进程多窗口），按计划进入 M1。

| POC | 核心判据 | 实测（release） | 结论 |
|---|---|---|---|
| POC-1 多窗口内存 | 单窗口 < 40MB；3 窗口 < 90MB | 单窗口 **33.7MB**；3 窗口 **47.4MB** | 通过 |
| POC-2 大仓库滚动 | 帧间隔 P95 < 33ms；滚动中内存无持续增长 | P95 **4.31ms**；RSS 15s 内 +0.1% | 通过 |
| POC-3 一致性 | 与 git CLI 输出一致 | **9/9 全部一致** | 通过 |
| POC-4 泳道增量布局 | 折叠/排序切换增量更新 < 50ms | 折叠 **20µs**；排序切换 **6.8µs** | 通过 |

同时发现并修复 2 个实现级缺陷与 1 个基准资产缺陷（见第 6 节），未发现架构级风险。

## 2. 环境与基准资产

- **基准仓库**（`scripts/gen-synthetic-repo.sh` 生成，完全可复现）：

  | 档位 | 提交数 | .git 体积 |
  |---|---|---|
  | small | 1,060 | 256 KB |
  | medium | 50,400 | 8.5 MB |
  | large | 1,001,000 | 167 MB |

- 图结构：一条 main 主线 + 周期性"分叉后立即合并"的旁支（覆盖长线性段与合并气泡）。

## 3. POC-1：Slint 软件渲染多窗口内存

**方法**：每个窗口承载 1 万行虚拟列表 + 6 列泳道占位列（模拟真实 Log 视图的
内存布局），挂起 45s 期间由外部采样进程 RSS。debug 构建。

| 场景 | 工作集 RSS | 私有内存 | 判据 |
|---|---|---|---|
| 单窗口（1 万行） | **33.7 MB** | 11.3 MB | < 40MB ✓ |
| 三窗口（各 1 万行） | **47.4 MB** | 25.8 MB | < 90MB ✓ |

**关键观察**：
- 后端确认为 `winit-software`（应用日志）。
- 每增加一个窗口的边际成本约 **6.8MB**（47.4 − 33.7 的一半量级），显著低于单窗口
  绝对值，说明 Slint 运行时与字体/渲染资源在多窗口间共享，符合架构规划 4.2 的预期。
- 与阶段 0 空窗口基线对比：阶段 0 三窗口空窗 32.5MB，本次三窗口**带 3 万行视图**
  为 47.4MB，增量约 15MB 属视图数据成本，仍远低于 90MB 判据。
- 作为参照，同条件 femtovg（GPU）后端在阶段 0 为 198.1MB（约 6 倍），软件渲染
  的低内存路线得到实证。

**边界说明**：本次为 debug 构建的空闲态 RSS；release 通常更低。M1 的 G1 门将以
release 构建复测。

## 4. POC-2：gix 大仓库虚拟化滚动

**方法**：`gix` revwalk 枚举 large 仓库全部提交 id；Slint `ListView` 只实例化可见行，
行文本由模型惰性 `find_commit` 解析并缓存（缓存上限 8192，验证内存有界）；1ms 定时器
连续推进滚动偏移（步长 4096 行）驱动重绘，采样相邻帧间隔。

| 指标 | debug | **release** | 判据 |
|---|---|---|---|
| 加载（revwalk 全量枚举 1,001,000 提交） | 22.92 s（4.37 万条/秒） | **4.23 s（23.65 万条/秒）** | — |
| 帧间隔 P50 | 27.11 ms | **1.05 ms** | — |
| 帧间隔 P95 | 32.24 ms | **4.31 ms** | < 33ms ✓ |
| 帧间隔 P99 | 34.67 ms | **4.98 ms** | — |
| 最大帧间隔 | 123.69 ms | 83.35 ms | — |
| 超 33ms 帧占比 | 2.99% | **0.004%（1/28195）** | — |
| 行解析平均延迟 | — | 0.005 ms/行 | — |
| 滚动期 RSS | 150.7 → 217.8MB（18s） | **209.5 → 209.7MB（15s，+0.1%）** | 无持续增长 ✓ |

**关键观察**：
1. **debug 与 release 差距达 6 倍**（P95 32.24ms → 4.31ms）。debug 下 P95 已贴近
   33ms 判据，release 下余量约 7 倍，结论以 release 为准。
2. **软件渲染后端不支持渲染回调**（`set_rendering_notifier` 返回错误），POC 自动
   降级为定时器采样 —— 这直接决定 M1/M5 的帧时间回归基准必须采用定时器口径，
   纳入 CI 时需固定采样方式。
3. **大仓库 RSS 由 mmap 的 pack 页主导**：167MB 的 packfile 被 gix 以 mmap 读取，
   被触碰的页计入 RSS（约 210MB ≈ 167MB pack + 约 40MB 进程自身），而**堆增长可以忽略**
   （15s 内 +0.1%，行缓存上限生效）。这是 mmap 零拷贝路线的固有特征，不是内存泄漏；
   对应缓解手段（`madvise` / 分段映射）列入 M1 待评项（第 6.5 节）。
4. 加载速率 23.65 万条/秒意味着：即便不做分页，100 万提交的全量枚举也在 5s 内；
   按架构规划的 500–2000 行分页，首屏可做到毫秒级。

## 5. POC-3：gix 与 git CLI 一致性

**方法**：对基准仓库与专用 fixture 仓库，逐项比对 gix 与 git CLI 的结构化输出。

| 对比项 | small | medium | large | 结果 |
|---|---|---|---|---|
| **A** 提交遍历（`git rev-list --all`） | 1,060 | 50,400 | 1,001,000 | 三个仓库提交集合**完全一致** |
| **B** 提交元数据（`%H\|%an\|%ae\|%at`） | 1,060 | 2,000 | 2,000 | 抽样逐条一致 |
| **C** 工作区状态（porcelain v1） | fixture：5 个变更路径一致（`M`/`D`/`A`/`??`/`M`） | — | — | 一致 |
| **D** 树差异（`--name-status`） | `HEAD~3..HEAD` 与 `HEAD~1..HEAD` 各 1 个变更 | — | — | 一致 |

**合计 9/9 通过。**

**未覆盖项（明确记录，不得静默带入 M1）**：
- **numstat 行数**（增删行计数）未纳入本轮对比：gix 侧需要 `blob-diff` 级别的内容
  差异统计，属 `gt-diff` 的 M1 工作范围。当前 D 项只比对**路径集合与变更类型**。
- C 项只比对**路径集合**，未比对 porcelain 的 XY 状态字母映射（gix 的
  `Item`/`ChangeRef` 到 porcelain 编码的映射表需在 `gt-backend` 中固化并加断言）。

**产出**：本对比程序即为需求侧"一致性测试套件 v0"的原型，按 M1 任务 1-11 工程化
进 `gt-backend` 并接入 CI。

## 6. POC-4：泳道图增量布局算法

**方法**：脱离 UI 的纯算法计时，合成图与基准仓库结构对齐（每 20 个提交一个合并气泡）。
全量布局对整个 100 万提交序列做一次泳道分配并每 4096 行留存状态检查点；
折叠/排序变化只从最近检查点重启、仅重排受影响区间。

| 指标 | debug | **release** | 判据 |
|---|---|---|---|
| 全量布局 1,000,000 提交（首次） | 92.0 ms | **4.23 ms** | — |
| 全量布局 P95（3 次复测） | 93.5 ms | **4.45 ms** | — |
| 折叠 / 展开线性分支（增量） | P95 674 µs | **P95 20 µs** | < 50ms ✓ |
| IntelliSort 式局部排序切换（单次） | 223 µs | **6.8 µs** | < 50ms ✓ |
| 过程峰值泳道数 | 2 | 2 | — |

**关键观察**：
1. **release 下全量布局 100 万提交仅 4.2ms**，即使退化为全量重排也远优于 50ms 判据；
   增量路径（20µs / 6.8µs）则进一步把代价降到可忽略。
2. **折叠不改变泳道分配**：折叠线性分支的增量重排中"改动行数 = 0"，即只有行的
   可见性映射变化，泳道索引不变 —— 印证了"只重排受影响泳道"可满足。
3. **非拓扑序输入是唯一边界风险**：以逆序（先旧后新）喂入 3000 个提交时，峰值泳道
   膨胀到 **3120**（拓扑序下为 2），耗时 105ms 并呈 O(n²) 趋势。原因是父提交已被
   消费，泳道持续等待永不出现的提交。**结论：lane 分配必须保证拓扑序输入**，
   这与 IntelliSort 的前提一致，需在 `gt-graph` 的接口契约中显式约束。

## 7. 发现的问题与修复

### 7.1 泳道泄漏（已修复，POC-4）
合并提交会让"主干泳道"与"侧枝泳道"同时指向汇合点；原实现消费汇合点时只释放其中
一条，另一条永久占位，泳道数随合并次数线性膨胀，单步查找退化为 O(泳道数)——
百万级仓库上表现为不收敛。修复为"所有等待同一提交的泳道汇合到最早一条，其余立即释放"。

### 7.2 基准资产缺陷：提交树完全相同（已修复）
原 `gen-synthetic-repo.sh` **只有首个提交写入文件**，其余提交不带任何 `M` 指令，
导致全部提交共享同一棵树：`git diff <root>..HEAD` 恒为空。这会让所有 diff/路径类
测试（POC-3 D、M1 的 FR-DIF、NFR-COR）空转而不报错。修复为**轮转引用 16 个内容
互异的 blob**，使相邻提交树不同，且唯一 blob 数保持常量、.git 体积不随提交数膨胀。
修复后 `git diff --name-status HEAD~3 HEAD` 正确输出 `M  file.txt`，三个仓库已重新生成。

### 7.3 软件渲染不支持渲染回调（设计约束，非缺陷）
`Window::set_rendering_notifier` 在 `winit-software` 后端不可用。POC-2 已降级为
定时器采样。**影响**：M5 的帧时间回归基准需固定为定时器口径，不可依赖渲染回调。
