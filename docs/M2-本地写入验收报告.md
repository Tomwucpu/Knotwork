## 4. 关键设计与取舍（写给后来者）

### 4.1 写操作为什么以 git CLI 为主，而不是 `gix-index`

路由表（架构规划 3.2）把"暂存 / 反暂存"的首要实现标为 `gix-index`。本阶段选了 CLI，理由与代价：

- **一致性优先**：直接写索引必须自己复刻 `.gitattributes` 的 `text`/`eol`、`core.autocrlf`、
  `core.filemode`、`core.symlinks` 与 intent-to-add 语义。任一处不完整，"我们暂存的内容"
  就与 `git add` 不同 —— 直接违反 NFR-COR-01（P0）。L3 套件证明当前实现与 CLI **逐字节一致**。
- **hunk / 行级仍按计划口径**：补丁由 `gt-diff` 生成，落库走 `git apply --cached [--reverse]`，
  也就是 `git add -p` 的底层机制。
- **代价**：每次写操作起一个子进程（10–40ms）。写操作是点击级低频操作，不触及 NFR-PRF-03
  的 200ms 感知阈值；读热路径（status / log / diff）仍在进程内走 gix。

### 4.2 写通道不参与代次作废

M1 的代次闸门语义是"同通道新请求作废旧请求"。把它套到写请求上会造成
**"点了提交、结果被后续请求作废丢弃"** —— 用户永远不知道提交是否生效。
因此 `RequestLane::Write` 单独成道且 `is_gated() == false`，`cancel_in_flight`
也刻意跳过写通道（刷新不该拦下一次正在执行的提交）。

### 4.3 补丁落库前的指纹校验

界面把"它看到的那份差异"的 `FileDiff::fingerprint()` 一起带上；服务层落库前
重算并比对，不一致就拒绝并要求刷新。原因是 hunk 下标是**位置**语义：
文件在用户选择期间被外部改动时，旧下标可能指向错误的位置。
`a_stale_fingerprint_blocks_the_patch` 把这条钉住。

### 4.4 行级选择的降级规则

未选中的**删除**行在补丁里降级为上下文，而不是直接丢弃 —— 否则补丁会少一行上下文，
后续行对不齐。这条规则写在 `gt-diff/src/patch.rs` 的模块文档里，并有专门用例
（`selecting_only_the_added_line_drops_nothing_else`）。

### 4.5 单实例守卫用回环 TCP

工作区禁止 `unsafe`，因此排除 Win32 命名互斥量/`WM_COPYDATA`；`std::net` 是纯安全 Rust，
且"连不上"天然等价于"没有主实例"。协议是行式文本 + 空行定界（必须有定界符：
客户端在收到 `OK` 前不会关闭连接，等 EOF 会互相干等），只接受已存在的本地路径，
主实例仍会做仓库校验与去重，因此这个通道不能被用来"命令主实例做什么"。

## 7. G2 结论

**有条件通过。**

- 写链路的**正确性**已用最强的方式钉住：L3 套件以"git 自己的输出"为基准，
  9 个用例覆盖暂存/反暂存/hunk/行级/丢弃/提交/修订/分支/忽略，全部逐字节一致；
- 写锁与单实例两项**在真实双进程场景下验证通过**，含残锁接管；
- 三项部分达标中，两项（FR-LOG-05 的视觉形态、FR-SET-02 的生效范围）属于
  **交付形态与消费者排期**问题，不涉及数据正确性；一项（FR-CMT-03 的 CRLF）
  是刻意不做一个会误报的启发式。

进入 M3 前建议：
1. 把"设置里的缓存预算"接到 `gt-service::cache`（否则该设置项在 M3 的网络操作下
   仍只是一个数字）；
2. M3 的 push/pull 会引入第一批**长时子进程**（网络 120s），届时把
   `GitCli::run_cancellable` 的取消路径与 Console 审计一起复核一遍 —— 该能力已在 M2
   备好并有单测，但还没有真实的网络场景压过。
