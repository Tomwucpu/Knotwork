## 2. G4 通过标准逐条结论

需求文档第 7 节对 M4 的验收口径是：
**"交互式 rebase 三典型序列 + 三路编辑器全场景 + 中断恢复"**；
实施计划第 7 节要求"操作等价测试（rebase 三典型序列、冲突三场景）+ G4 评审"。

| # | 标准 | 结论 | 证据 / 说明 |
|---|---|---|---|
| ① | 交互式 rebase 三典型序列 | **达标** | squash 合并 WIP、drop 中间提交、reword 消息三条序列均与"手写待办列表的 `git rebase -i`"逐值一致：`interactive_rebase_squash_matches_a_cli_todo` / `..._drop_matches_a_cli_todo` / `..._reword_matches_a_manual_amend` |
| ② | 三路编辑器全场景 | **达标（文本场景）** | 逐块四选一（左 / 右 / 双方 / 基线）、手写中心栏、整文件取一侧、按标记全取；`git ls-files -u` 在标记为已解决后清空（`conflict_flow_through_the_service_clears_unmerged_entries`）。CRLF 与中文在解析层单测覆盖；**二进制冲突**只能整文件取一侧（见 §5-D） |

| ④ | 危险操作二次确认 | **达标** | 硬重置、跳过变基、删除贮藏、整文件取一侧、中止进行中操作、强制删除分支、丢弃修改 —— 全部经 `Confirm`，文案均包含"失去什么 / 不可逆 / 替代做法"三要素 |

## 4. 关键设计与取舍（写给后来者）

### 4.1 整层走 git CLI，不做 git2 集成层（对计划 4-1 的偏离）

计划把 4-1 定为"git2 集成层（merge / revert 底座）"，路由表也把 merge / cherry-pick /
revert 的主实现标为 `git2`。本次统一选了 CLI，理由不是省事：

1. **验收口径就是"与 CLI 等价"**（需求文档 9 节 L3）。走 CLI 时等价性是构造出来的；
   走 libgit2 则要逐项对齐它与 git 本体的差异（合并策略、`merge.renormalize`、`rerere`、
   `merge.conflictStyle=zdiff3` 的标记形态、`core.autocrlf` 的落盘时机）。
2. **hooks 必须在场**：`merge` 会触发 `pre-merge-commit` / `commit-msg`，`revert` 会触发
   `commit-msg`。用户装了 hook 就是要求它生效，绕过它等于行为不一致。
3. **冲突标记的形态由 git 决定**：三路编辑器解析的就是工作区里的标记。若自己写标记，
   就会出现"我们写一套、用户在终端里 `git merge` 得到另一套"，FR-CFL-03 立刻失真。
4. **不引入 C 工具链依赖**：`git2` 需要编译 libgit2，与"轻量、可复现构建"相悖。

计划 4-1 真正要解决的约束**没有丢**：`git2` 的 `Repository` 不能并发写，CLI 同样不能并发跑
（`index.lock` 会互相踩）。因此服务层给每个仓库加了一把**高级操作独占槽位**
（`RepoHandle::begin_advanced`），同一仓库同时只允许一个高级操作，冲突时立刻给出
"已有高级操作在进行（X）"而不是让用户等一个 index 锁超时。

### 4.2 交互式变基怎么在没有编辑器的进程里落地

交互式变基的本质是"序列编辑器"：git 把待办列表写到临时文件，等编辑器改完后按列表执行。
GUI 进程里没有编辑器，也**不能**起真实编辑器（会挂到超时）。做法是：

```text
GIT_SEQUENCE_EDITOR="cp '<我们生成的 todo>'"  git rebase -i --no-autosquash <base>
GIT_EDITOR=true
env GIT_MERGE_AUTOEDIT=no
```

三个变量各解决一件事：

- `GIT_SEQUENCE_EDITOR=cp` 让我们**自己生成待办列表**，计划的顺序与动作即执行内容；
- `GIT_EDITOR=true` 让 `squash` 合并消息时直接采用 git 拼好的默认消息。不设它，
  git 会尝试启动编辑器 —— 在无终端的进程里就是一次挂到 300s 超时的死等。
- `GIT_MERGE_AUTOEDIT=no` 让合并提交不进入编辑器。

`reword` 不用 git 的 `reword` 指令，而是 `pick` + 紧跟一条
`exec git commit --amend -F <消息文件>`。理由：`reword` 需要**第二个**编辑器回调
（走 `GIT_EDITOR`），多一个可失败的环节，而且要解决"此刻编辑的是哪个提交"的识别问题；
`exec` 由 git 在该提交之后执行，语义确定。

中断时**必须保留**临时计划目录：待办列表还引用着消息文件，用户 `--continue` 时
`exec` 行还要再读一次。成功后才清理（这是最容易踩的坑，代码里已标注）。

### 4.3 冲突解析在 `gt-diff`，按标记而不是按 stage

解析磁盘上的标记而不是直接读 `:1:/:2:/:3:`，有三个好处：上下文天然对齐（结果列就是文件本身）、
块边界即冲突边界（不必再对两侧做 diff 猜边界）、FR-CFL-03 的"按标记解析"与主流程共用一套代码。

代价是依赖工作区里确实有标记；`merge.conflictStyle=union` 或用户手工删掉标记时
`has_markers == false`，此时界面**拒绝**"标记为已解决"，引导用户改用"整文件取一侧"——
硬写会把文件写成一份丢失内容的文本。

**行尾保真**是这一层的另一个重点：解析按 `\n` 切分并保留每行的 `\r`，重建时沿用原文的
行尾风格与"是否有末尾换行"。任何一处走样都会让"解决冲突"变成"顺手改了整个文件的行尾"。

### 4.4 三侧内容用 `git show :2:` 而不是从标记里猜

"整文件取当前分支 / 合入分支"读的是索引里的 stage 对象（`:2:` / `:3:` / `:1:`），
而不是解析标记后再拼。原因：二进制冲突、一方删除、CRLF 归一化这三种情况下，
标记文本都不足以还原原始字节。为此 `CliOutput` 增加了 `stdout_bytes` 字段 ——
有损 UTF-8 解码会把图片、GBK 文本改坏。

### 4.5 高级操作槽位为什么是 RAII

合并 / 变基 / 拣选的失败路径很多（冲突、取消、git 报错、计划非法）。任何一条漏掉
"释放槽位"，该仓库此后就再也发不出高级操作。M3 的网络独占槽位踩过这个坑
（"一次取消之后 fetch 按钮永久失效"），所以这里用 `Drop` 释放，而不是在每条路径上手写清理。

### 4.6 变基进度为什么直接读 `.git` 文件

`rebase-merge/msgnum` 与 `end` 就是 git 自己维护的进度。读两个小文件即可，
不需要为此起子进程，也不需要为了读进度而要求 git CLI 存在（文件读取是纯 fs 操作）。
`rebase-apply`（`am` 风格）用 `next` / `last`。

### 4.7 合并提交必须显式提示

`git rebase -i` 默认不保留合并提交（等价 `--no-rebase-merges`）。一个含合并的分支做
交互式变基后历史形状会变，这是**用户必须知道的事实**，因此计划里单独统计
`merges_dropped` 并在编辑器摘要里以 ⚠ 明示。

### 4.8 通用操作对话框而不是五个遮罩

合并 / 变基 / 重置 / 生成补丁 / 应用补丁 / 新建标签的交互形态完全一致（填一个参数 + 选一个模式 + 确认）。
做成一个对话框由 `OpKind` 分派，Slint 与接线各少五份几乎相同的代码；
"哪一项是危险色""哪个模式需要第二个输入框"集中在一处判定。

| H | 真实仓库规模下的交互式变基（数百提交 + hook） | 用例覆盖 2–3 个提交的序列；超时设为 300s 且可取消 | 在含 pre-commit hook 的仓库上跑一次 100+ 提交的 squash 序列，确认进度面板与取消行为 |
| I | 平台差异（`cp` / `true` 是否存在于 git 的 sh 环境） | Windows（git for Windows）实测通过；git 依赖 sh，因此 Unix 同样成立 | macOS / Linux 各跑一次交互式变基用例（M5 横向补齐时） |

### 5.3 已知差异（刻意保留）

|---|---|---|

### 6.2 L3 用例清单（`gt-service/tests/advanced_ops.rs`）

| 用例 | 断言方式 |
|---|---|
| `merge_no_ff_matches_the_cli` | `HEAD^{tree}` / 提交消息序列 / status / 引用名两侧一致 |
| `merge_conflict_lists_the_same_files_as_the_cli` | 冲突文件清单与 `git diff --diff-filter=U` 逐字相同 |
| `rebase_conflict_then_continue_matches_the_cli` | 冲突 → 写解决结果 → continue 后状态一致 |
| `interactive_rebase_squash_matches_a_cli_todo` | 与"手写 `pick` + `squash` 待办列表"的 `git rebase -i` 结果一致 |
| `interactive_rebase_drop_matches_a_cli_todo` | 同上（`drop`） |
| `interactive_rebase_reword_matches_a_manual_amend` | 与"pick 后 `git commit --amend -F`"一致 |
| `cherry_pick_matches_the_cli` | 含 `-x` 来源行，树与消息一致 |
| `revert_matches_the_cli` | 反向提交后树与消息一致 |
| `reset_modes_match_the_cli` | soft / mixed / hard 三档分别对照（含未提交改动） |
| `stash_apply_and_pop_match_the_cli` | 含 `-u`；apply 后工作区一致，pop 后两边都不再有贮藏 |
| `patch_generated_here_applies_like_the_cli` | 我们生成的补丁由 git 自己应用后状态一致 |
| `tag_operations_match_the_cli` | 标签类型与指向一致 |
| `conflict_flow_through_the_service_clears_unmerged_entries` | 服务层全链路：冲突 → 清单 → 解析 → 逐块求解 → 落盘 → `git ls-files -u` 为空 → 合并提交后干净 |
| `a_failed_advanced_operation_releases_the_slot` | 失败的合并不残留槽位（下一次高级操作可执行） |

**为什么比 `HEAD^{tree}` 与消息而不是提交 id**：提交 id 含 committer 时间，
两侧执行时刻不同就必然不同；tree + 消息 + 顺序一致已经蕴含"内容与结构一致"。

## 7. G4 结论

**有条件通过。**

- 交互式变基这一"最大的单项工程"落地方式是可解释的：计划 → 待办列表 → git 自己执行，
  三条典型序列都以"手写待办列表的 `git rebase -i`"为基准逐值比对；
- 三路编辑器的正确性由数据层保证（解析、求解、行尾保真都是纯函数并有单测），
  而非靠"看起来对"；
- 中断恢复（merge / rebase / conflict 三场景）与危险操作的二次确认逐项覆盖，
  且中止后分支确实回到原位（有断言）；
- L3 从 6 个用例扩展到 20 个（M3 6 + M4 14），覆盖 M4 全部 P0 能力的等价性；
- **未完成的是界面的人工点击走查**与三项功能边界（重排序、任意两提交比较、多提交多选）。
  前者需要人眼在窄窗口下确认观感，后者是明确的 v1.0 增强项，均不涉及正确性。

进入 M5 前建议：

1. 先做一轮人工走查（右键菜单位置、三路编辑器在 1280×860 下的可读性、变基编辑器长列表滚动），
   把结果附到本报告后即可关闭 G4 的界面项；
2. M5 的 Blame 与文件历史会复用本轮的三路编辑器与 Log 上下文菜单，届时统一交互细节；
3. 合并 M3 的遗留项（真实 SSH/HTTPS 双路径验收）与 M4 的走查一并完成，作为 v1.0 发布评审的输入。
